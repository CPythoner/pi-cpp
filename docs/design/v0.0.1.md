## 0. 本篇位置

pi-cpp 是一个学习型项目：用 **C++17** 重写 pi coding agent 的核心能力。行为与 wire 语义以 pi `v0.80.0` 为规范来源；Tau `v0.4.1` 用于辅助理解模块划分、算法和实现方式，不作为行为规范来源。

本篇是系列第一篇：**打地基**。没有网络 Provider、Agent 主循环和真实 coding tools，交付的是让后续实现成为可能的三样东西：跨平台构建骨架、消息/事件类型系统，以及 C++17 下的取消与线程基础设施。

## 1. 背景与动机

### 1.1 为什么第一步是“类型”而不是能跑的 Agent

pi 的核心不是某一个 CLI，而是一组层层复用的契约：Provider 产出 LLM/流式事件，Agent 消费这些事件并管理 turn/tool 生命周期，coding-agent 再组合工具、session、配置与前端能力。无论 C++ 最终采用何种类设计，消息、事件、停止原因、usage、tool call 等 wire 数据必须先稳定下来。

`v0.0.1` 先用聚合类型 target `pi_types` 验证 C++17 `std::variant` + JSON 序列化方案。该 target 只服务于本版本的地基搭建，不定义项目长期 SDK 边界；`v0.0.2` 开始按 SDK-first 原则将能力归属到 `ai`、`agent`、`coding-agent` 三层。

### 1.2 wire 兼容是硬约束，但手工 fixture 不是兼容证明

项目从第一天就按 camelCase wire 格式设计消息和事件，避免先写一套 C++ 私有 DTO、后续再堆 adapter。

需要区分两个概念：

1. **wire-first 设计**：`v0.0.1` 已完成，类型字段、判别字段和 round-trip 都围绕 pi 的 wire 形态设计。
2. **真实兼容证明**：`v0.0.1` 不以此为验收目标。当前三个 JSONL fixture 是手工构造样本，只证明本项目内部序列化自洽，不能证明与 pi `v0.80.0` 的真实输出一致。

从 `v0.0.2` 起，兼容门采用：**真实 pi `v0.80.0` fixture + reference harness + differential trace**。Tau fixture 只能作为辅助回归。

### 1.3 为什么现在就要 CancellationToken

pi 的 AbortSignal 贯穿 Provider 流取消、Agent abort、tool 取消和后续 bash 进程树终止。项目坚持 C++17，所以需要自己的取消抽象。

`v0.0.1` 先建立 CancellationToken 基础接口和测试；当前实现的 `request()` 仍在持有内部 mutex 时执行用户 callback，这一实现限制不能带入真实网络和工具生命周期。

因此本项目只声明 CancellationToken 提供项目所需的取消模型，不宣称与 `std::stop_token` 完全等价。`v0.0.2` 在接入真实 HTTP 前完成 callback 锁外执行、unregister/request 并发和析构竞态加固。

## 3. 原理讲解

### 3.1 消息双层模型

pi 区分 LLM 世界的消息与 Agent 应用世界的消息。Agent session 需要保留比 Provider 请求更多的信息，例如 bashExecution、custom、branch summary、compaction summary；真正发送给模型时再通过 `convertToLlm` 降维。

`v0.0.1` 用 `std::variant` 表达这类 tagged union：

```cpp
using ContentBlock = std::variant<
    TextContent,
    ThinkingContent,
    ImageContent,
    ToolCall>;

using AgentMessage = std::variant<
    UserMessage,
    AssistantMessage,
    ToolResultMessage,
    BashExecutionMessage,
    CustomMessage,
    BranchSummaryMessage,
    CompactionSummaryMessage>;
```

该值语义建模作为后续实现基础继续保留；`v0.0.2` 重点调整的是类型所属 SDK 和 public header 位置，而不是推翻 `variant` 方案。

### 3.2 错误即消息

普通 Provider 错误不应让 Agent 进程因为异常直接崩溃。`AssistantMessage` 因此包含 `StopReason::Error` / `StopReason::Aborted` 以及可选错误信息。后续 Agent loop 基于这些可观察结果正常收尾。

### 3.3 L1 与 L2 事件

- **L1 Provider events**：描述一个 AssistantMessage 如何流式生成，包含 start / text_* / thinking_* / toolcall_* / done / error。
- **L2 Agent events**：描述 Agent 生命周期，包含 agent/turn/message/tool_execution 的 start/update/end。

`v0.0.1` 为了先验证 wire 和 variant，将 L1/L2 暂时都放在 `src/agent/events.hpp`。长期责任边界固定为：

```text
ai            -> Provider / L1 events / EventStream / cancellation
agent         -> AgentMessage / AgentEvent(L2) / Agent / AgentTool
coding-agent  -> CodingAgent / tools / session / config / catalog
```

`v0.0.2` 在实现 Provider 前先完成这一层次迁移。

### 3.4 `std::variant` + `std::visit`

TS 的判别联合在 C++17 中最自然的映射是 `std::variant`。项目使用一个小型 `overload` helper：

```cpp
template <class... Ts>
struct overload : Ts... { using Ts::operator()...; };

template <class... Ts>
overload(Ts...) -> overload<Ts...>;
```

相比继承 + `dynamic_cast`，其优势是值语义、无需为每条消息做独立堆分配，并能在新增 variant alternative 时让遗漏处理尽早暴露为编译问题。

### 3.5 nlohmann/json 序列化规则

以 `nlohmann/json 3.11.3` 的本项目实测行为为准：

- 不含 optional、且字段映射简单的结构可用 NLOHMANN 宏。
- 含 optional 的结构手写 `to_json/from_json`。
- `nullopt` 序列化为**字段省略**，而不是 JSON null。
- variant 的 `role` / `type` 判别字段由分发层显式写入。
- NLOHMANN 宏在 `namespace pi` 内使用。

这些规则既避免依赖未经验证的库行为，也能更精确控制 pi wire 语义。

### 3.6 CancellationToken 当前约束

C++17 下使用 `atomic<bool> + mutex + condition_variable + callback registry` 可以提供项目需要的取消能力，但具体并发语义必须由测试定义。

`v0.0.1` 的接口包括：

```cpp
class CancellationToken {
public:
    using Callback = std::function<void()>;

    void request();
    bool requested() const noexcept;
    bool wait_for(std::chrono::milliseconds timeout) const;
    std::uint64_t registerCallback(Callback cb);
    bool unregisterCallback(std::uint64_t id);
};
```

当前 callback-under-lock 行为只属于实现限制，不属于长期 public contract。`v0.0.2` 将改为锁内完成状态切换与 callback snapshot/detach，解锁后再执行用户 callback，并补齐 unregister/request/destructor 竞态测试。

## 5. wire 契约

### 5.1 判别字段

| 层级 | 判别字段 | 典型取值 |
|---|---|---|
| AgentMessage | `role` | user / assistant / toolResult / bashExecution / custom / branchSummary / compactionSummary |
| ContentBlock | `type` | text / thinking / image / toolCall |
| L1 event | `type` | start / text_start / text_delta / text_end / thinking_* / toolcall_* / done / error |
| L2 event | `type` | agent_start / agent_end / turn_start / turn_end / message_start / message_update / message_end / tool_execution_* |

规范来源顺序固定为：

> **pi `v0.80.0` 可观察行为 > 本项目兼容规范 > Tau `v0.4.1` 实现参考**

字段、判别值和事件语义均以 pi `v0.80.0` 为第一来源；Tau 只辅助理解实现。

### 5.2 手工黄金样本

`v0.0.1` 使用三类手工 JSONL 样本：

- `session_minimal.jsonl`：header + user + assistant。
- `session_toolcall.jsonl`：assistant toolCall + toolResult。
- `session_thinking.jsonl`：thinking + text + usage + stopReason。

测试执行 parse → dump → JSON 语义比较，不依赖字段顺序。

这些样本定位为**内部回归样本**。真实 pi `v0.80.0` 基线证据由 `v0.0.2` 的 `tests/fixtures/pi-v0.80.0/` 与 differential harness 提供。

### 5.3 序列化规则

最终实现采用以下约定：

```cpp
void to_json(nlohmann::json& j, const AgentMessage& m) {
    std::visit(overload{
        [&](const UserMessage& v)      { j = v; j["role"] = "user"; },
        [&](const AssistantMessage& v) { j = v; j["role"] = "assistant"; },
        // ...
    }, m);
}
```

- 具体 wire struct 可以使用宏或手写 serializer。
- variant 判别字段由 variant serializer 负责。
- optional 字段按实际 wire 规则手写并在 `nullopt` 时省略。
- 未知 role/type 显式报错。
- 未知普通字段策略以 pi `v0.80.0` 真实 fixture/parser 行为为准，不单凭 Tau 推断。

## 6. 关键设计决策

### 决策 1：`std::variant` 而不是继承层级

采用 `std::variant` + `std::visit`。它与 pi 的 tagged union 模型自然对应，也更适合 C++17 值语义。

### 决策 2：wire 成员使用 camelCase

wire DTO 直接映射 JSON 字段，减少转换层。限定范围是 wire/domain data；内部实现类型仍可遵循普通 C++ 命名习惯。长期 public SDK 是否所有对象都保留 wire 命名，在 `v0.3.0` API freeze 前统一审计。

### 决策 3：L1 delta 携带完整 partial

`v0.0.1` 采用值语义，优先保证正确性和线程边界清晰。若 Provider streaming profile 证明拷贝成为热点，再优化内部持有方式；不得为了性能改变可观察事件语义。

### 决策 4：未知字段 / 未知判别值

当前策略是未知 role/type 显式失败；未知普通字段策略需要通过 pi `v0.80.0` 真实 fixture 和 parser 行为最终确认。兼容策略不能只从 Tau 推断。

### 决策 5：CancellationToken 提前实现

CancellationToken 在 `v0.0.1` 提前建立，因为取消链是后续 Provider、Agent、Tool、process 的公共基础设施。

callback 注册顺序、幂等 request、wait 唤醒等核心能力有测试；callback-under-lock 不定义为 public contract，并在 `v0.0.2` 网络接入前修正。

### 决策 6：三平台 CI 从第一天开始

Linux/macOS/Windows 从第一版进入 CI。Windows 多配置生成器、编译器警告和标准库差异越早暴露，修复成本越低。

### 决策 7：SDK-first 从 v0.0.2 建立

`v0.0.1` 只验证类型和基础设施，尚不承担最终 SDK packaging。继续实现 Provider 前必须先建立 `ai` / `agent` / `coding-agent` 的 public/private 边界，避免 CLI 和核心能力围绕 `pi_types + PUBLIC src` 继续耦合。

## 8. 总结与下篇预告

`v0.0.1` 验证了三个关键前提：C++17 + `std::variant` 可以表达 pi 的主要消息/事件 union；三平台工程骨架可以稳定工作；取消、线程、JSON 等基础设施可以在进入网络与主循环之前独立测试。

本版本还明确留下两个必须在 `v0.0.2` 先解决的问题：

1. `pi_types + src/ PUBLIC include` 只适合作为地基阶段过渡结构，下一版必须建立真正的 SDK 边界。
2. CancellationToken callback-under-lock 不能直接带入真实 Provider/Tool 生命周期。

因此下一篇 `v0.0.2` 先完成 **SDK 边界重构**，再进入 Provider/SSE：

```text
ai
 ↓
agent
 ↓
coding-agent
```

三层都以“外部 C++ 调用者可以独立消费”为设计前提。

## 附录 D：实现回顾

**结果**：T1-T12 全部完成。6/6 测试目标、63 个用例全绿（smoke 1 + string 4 + cancel_token 11 + thread_guard 7 + message_json 26 + events_json 14）；release/debug 双预设从零构建通过；`picpp --version` → `picpp v0.0.1`；第一方代码 `-Wall -Wextra -Werror` 零警告。

### 与设计的偏差

1. **nlohmann/json 3.11.3 在本项目实测不直接支持 `std::optional`**。8 个含 optional 字段的结构改为手写 `to_json/from_json`，并确立 `nullopt → 字段省略` 的规则。
2. NLOHMANN 宏必须在 `namespace pi` 内调用；全局作用域的 `pi::` 限定名形式无法按原方案工作。
3. `pi_types` 对 `nlohmann_json` 的链接从 INTERFACE 调整为 PUBLIC。
4. CMake 3.26 不允许无源 STATIC library；T1 先用 INTERFACE，加入源码后转 STATIC。
5. Windows/多配置 preset 需要显式 `configuration`，不能使用不存在的 buildPreset `args` 字段。
6. FetchContent 下 nlohmann target 名、fmt/doctest 选项和 CMake policy 均按真实构建行为修正。
7. `CMAKE_CXX_EXTENSIONS OFF`、`overload` 进入 `namespace pi`、doctest main 与 CombinedCancellation 都按实现反馈调整。

### 踩坑记录

- C++ TDD 的红态常表现为编译/链接失败，而不是运行时断言失败。
- doctest 某些断言宏对字符串拼接/不可 stringify 类型有约束。
- `-Wmissing-field-initializers` + `-Werror` 对聚合初始化非常敏感。
- variant 的 role/type 是分发层职责，测试具体 struct 时不能误以为判别字段会自动出现。
- LSP 对 generated header / 尚未拉取依赖的诊断不如真实 CMake build 可信。
- Windows VS 多配置生成器和 libstdc++/doctest 差异证明了“三平台第一天”是必要约束。

### v0.0.1 遗留问题

- CancellationToken callback 需要在 `v0.0.2` 改为锁外执行，并补并发/析构竞态测试。
- 真实 pi `v0.80.0` fixture + differential harness 在 `v0.0.2` 建立。
- EventStream 由 `v0.0.2` 实现，并归属 `ai` SDK public contract。
- 完整 SessionHeader / SessionEntry wire 模型在 `v0.1.0` 稳定。
- `pi_types + PUBLIC src` 在 `v0.0.2` 拆分为三层 SDK target 和 public headers。

## 附录 E：v0.0.2 SDK 边界要求

### E.1 三层名称固定为 ai / agent / coding-agent

项目与 pi 包名保持一致：

```text
external C++ app / picpp CLI / TUI
                 │
                 ▼
            coding-agent
                 │
                 ▼
               agent
                 │
                 ▼
                ai
```

三层都必须能作为独立 SDK 被外部工程调用。

### E.2 public header 从 src/ 迁出

目标目录：

```text
include/pi/ai/
include/pi/agent/
include/pi/coding-agent/

src/ai/
src/agent/
src/coding-agent/
```

规则：

- `include/pi/...` 才是 public API。
- `src/...` 只放 `.cpp` 和 private/detail headers。
- `${PROJECT_SOURCE_DIR}/src` 不得出现在 SDK target 的 PUBLIC include path。
- CLI/TUI 只能通过 public SDK API 调用核心能力。

### E.3 CMake SDK target

目标导出 target：

```cmake
pi::ai
pi::agent
pi::coding-agent
```

C++ namespace 因为 `-` 不能作为标识符，对应使用：

```cpp
pi::ai
pi::agent
pi::coding_agent
```

依赖严格单向：

```text
pi::coding-agent -> pi::agent -> pi::ai
```

### E.4 v0.0.1 类型在 v0.0.2 的归属

| 类型/能力 | 长期归属 |
|---|---|
| Provider message/model/usage、L1 events、EventStream、Cancellation | `ai` |
| AgentMessage、L2 AgentEvent、Agent、AgentTool、queue mode | `agent` |
| CodingAgent、read/write/edit/bash、session、config、catalog | `coding-agent` |

迁移时优先保持 wire 行为，不为了整理目录无谓改变 JSON contract。

### E.5 为什么在 v0.0.2 就完成 SDK 拆分

Provider、Agent loop 和 coding tools 一旦继续围绕 `pi_types + PUBLIC src` 生长，后续再拆 SDK 会同时牵动 include、CMake dependency、生命周期、测试和 public API。`v0.0.1` 代码量仍小，因此 `v0.0.2` 是建立 SDK 边界的最低成本窗口。

从 `v0.0.2` 起，每层至少增加一个 external consumer build/link test，确保 SDK 边界是 CI 可执行约束，而不是只存在于文档中。
