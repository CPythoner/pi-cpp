## 1. 背景与动机

### 1.1 为什么第一步是「类型」而不是能跑的 agent

pi 的分层里，`packages/agent/src/types.ts`（428 行）定义了全系统的契约：LLM 调用层（pi-ai）的**输出**是这些类型，agent 主循环的**输入**是这些类型，会话持久化的**存储单元**是这些类型，TUI 渲染的**数据源**还是这些类型。tau 的施工日志（`dev-notes/` phase 1）同样从核心类型开始——先定契约再写实现，避免边写边改类型导致全线返工。

如果我们跳过这一步直接写主循环，会立刻发现：流式回调的参数是什么？工具结果怎么表达？会话文件里每行是什么？——全都需要这些类型。

### 1.2 wire 兼容是硬约束

pi 与 tau 的会话文件（JSONL）理论上可以互读——因为两边都遵守同一套 **camelCase JSON 字段别名**（tau 用 Pydantic 的 `serialize_by_alias` 强制，见 `tau/src/tau_agent/messages.py:23-32`）。pi-cpp 的目标之一是加入这个互操作圈：**我们的会话文件，pi/tau 能读；它们的会话文件，我们也能读**。这要求类型系统从第一天起就按 wire 格式设计，而不是先随便定义再 adapter 转换。

### 1.3 为什么现在就要 CancellationToken

pi 的架构里 AbortSignal 是一等公民，贯穿 LLM 流取消、工具中止、进程树 kill（`pi-architecture.md` §4.6）。C++20 的 `std::stop_token` 正好对应这套语义，但我们选了 C++17——所以必须自己补齐这个原语，而且要在 v0.0.1 就位（v0.0.2 的网络线程马上要用）。它一旦有竞态 bug，会污染后面所有版本，所以作为一等公民交付并完整测试。

## 3. 原理讲解（学习篇）

### 3.1 pi 侧的机制

**① 消息双层模型**。pi 区分两套消息宇宙：`Message`（LLM 世界，只有 user/assistant/toolResult 三角色）和 `AgentMessage`（应用世界，在这三种之上加 bashExecution、custom、branchSummary、compactionSummary）。会话日志存 AgentMessage（完整），发给 LLM 前经 `convertToLlm` 降维（`pi/packages/agent/src/types.ts:305-314`）。本篇定义的是**全集** AgentMessage——它是会话文件的存储单元。

**② 错误即消息**。pi 的 StreamFn 契约规定 LLM 调用失败不得抛异常，必须编码为 `stopReason: "error"|"aborted"` 的 AssistantMessage（`types.ts:17-26`）。所以 StopReason 枚举里有 error/aborted，AssistantMessage 有 errorMessage 字段——这不是补丁，是设计。

**③ 内容块（ContentBlock）**。消息的 content 不是字符串而是**块数组**：text / thinking（含签名与 redacted）/ image（base64）/ toolCall（含增量参数 JSON）。流式输出时每个块都有 start/delta/end 生命周期——这正是 L1 事件的形态。

**④ 事件双层级**。L1（provider 事件）描述「一个 assistant 消息如何流式长出来」：text_delta 带 `contentIndex + delta + 全量 partial`；L2（agent 事件）描述「agent 生命周期」：turn_start/end、message_start/update/end、tool_execution_start/update/end。TUI 只消费 L2（经 tau 验证足以驱动完整 UI）。

### 3.2 C++17 技术点

**① `std::variant` + `overload` 访问模式**。TS 用 tagged union（`{type:"text", ...}`），Python 用 Pydantic 判别联合，C++17 的对应物是 `std::variant` + `std::visit`。经典写法需要一个 5 行的 overload 工具（C++17 推导指引）：

```cpp
template <class... Ts> struct overload : Ts... { using Ts::operator()...; };
template <class... Ts> overload(Ts...) -> overload<Ts...>;
```

**② 递归 variant 的规避**。`AgentMessage` 的 content 是 `ContentBlock` 数组，`ContentBlock` 不包含消息——两级 variant 是**无环**的。这是 pi 类型设计里隐藏的聪明之处：块不引用消息、消息不引用事件，一切单向，variant 可以直接表达。（若未来需要自引用类型，就得 `std::unique_ptr` 或前向声明+variant 间接层，本篇不需要。）

**③ nlohmann/json 的 ADL 序列化**。为类型提供 `to_json/from_json` 自由函数（ADL 查找），`nlohmann::json::get<T>()` 即可双向转换。宏 `NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE` 能自动生成，但字段名必须 C++ 与 JSON 同名——见决策 3（我们对 wire 类型直接用 camelCase 成员名）。`std::optional` 原生支持（缺字段 ↔ nullopt）。

**④ FetchContent + SYSTEM**（CMake ≥3.25）。依赖以 `SYSTEM` 方式引入后，其头文件的警告不污染 `-Werror`；全部 `FetchContent_Declare` 前置、pin 到精确 tag（`pi-architecture.md` 未覆盖，来源为 CMake 官方文档与选型调研）。

**⑤ 条件变量 + 原子_bool = 取消令牌**。`std::stop_token` 的本质是「一次性广播」：request 后所有 wait 立即返回、回调只执行一次、幂等。C++17 用 `std::atomic<bool> + std::condition_variable + std::mutex`（保护回调表）实现，坑在析构顺序与虚假唤醒——测试用例专门覆盖。

    std::int64_t timestamp = 0;

// ===== src/util/cancel_token.hpp =====
#pragma once
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <cstdint>
#include <functional>
#include <map>
#include <mutex>

namespace pi {

// 语义对齐 std::stop_token（C++20）：一次性广播、幂等 request、回调恰好一次。
// v0.0.1 交付并全测；未来升 C++20 可平替为 jthread/stop_token。
class CancellationToken {
public:
    using Callback = std::function<void()>;
    using Clock = std::chrono::steady_clock;

    void request();                       // 幂等；已注册回调在锁内执行后清除
    bool requested() const noexcept { return cancelled_.load(std::memory_order_acquire); }

    // 返回是否因 cancel 返回（false = 超时）；容忍虚假唤醒
    bool wait_for(std::chrono::milliseconds timeout) const;

    // 已取消则立即同步执行并返回 0；否则注册，cancel 时在 request() 线程执行
    std::uint64_t registerCallback(Callback cb);
    bool unregisterCallback(std::uint64_t id);   // 取消注册（若尚未执行）

private:
    mutable std::mutex mtx_;
    mutable std::condition_variable cv_;
    std::atomic<bool> cancelled_{false};
    std::uint64_t nextId_ = 0;
    std::map<std::uint64_t, Callback> callbacks_;
};

// 组合令牌：任一取消则整体取消（对应 pi 的 combineAbortSignals）
class CombinedCancellation {
public:
    explicit CombinedCancellation(std::initializer_list<std::shared_ptr<CancellationToken>> tokens);
    ~CombinedCancellation();              // 析构先移除回调再返回
    const CancellationToken& token() const;
};

} // namespace pi

// ===== src/util/thread_guard.hpp =====
#pragma once
#include <thread>
#include <utility>

namespace pi {
// RAII：析构时 join（若 joinable）。替代 C++20 jthread 的自动 join。
class ThreadGuard {
public:
    explicit ThreadGuard(std::thread t) noexcept : t_(std::move(t)) {}
    ThreadGuard(ThreadGuard&& o) noexcept : t_(std::move(o.t_)) {}
    ThreadGuard& operator=(ThreadGuard&&) noexcept;   // 移动赋值：先 join 自己持有的
    ~ThreadGuard();                                    // join if joinable
    bool joinable() const noexcept { return t_.joinable(); }
    void join();
    std::thread::id get_id() const noexcept { return t_.get_id(); }
    ThreadGuard(const ThreadGuard&) = delete;
    ThreadGuard& operator=(const ThreadGuard&) = delete;
private:
    std::thread t_;
};
} // namespace pi

### 5.4 序列化实现模式

具体结构体用宏生成（字段名 camelCase 与 wire 一一对应）：

```cpp
NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE_WITH_DEFAULT(pi::TextContent, text, textSignature)
NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE_WITH_DEFAULT(pi::ToolResultMessage,
    toolCallId, toolName, content, details, isError, timestamp)
```

variant 的分发手写（以 AgentMessage 为例）：

```cpp
void to_json(nlohmann::json& j, const AgentMessage& m) {
    std::visit(overload{
        [&](const UserMessage& v)            { j = v; j["role"] = "user"; },
        [&](const AssistantMessage& v)       { j = v; j["role"] = "assistant"; },
        [&](const ToolResultMessage& v)      { j = v; j["role"] = "toolResult"; },
        [&](const BashExecutionMessage& v)   { j = v; j["role"] = "bashExecution"; },
        [&](const CustomMessage& v)          { j = v; j["role"] = "custom"; },
        [&](const BranchSummaryMessage& v)   { j = v; j["role"] = "branchSummary"; },
        [&](const CompactionSummaryMessage& v){ j = v; j["role"] = "compactionSummary"; },
    }, m);
}
void from_json(const nlohmann::json& j, AgentMessage& m) {
    const auto role = j.at("role").get<std::string>();
    if      (role == "user")              m = j.get<UserMessage>();
    else if (role == "assistant")         m = j.get<AssistantMessage>();
    // ... 未知 role 抛 std::runtime_error（带 role 值，便于诊断）
}
```

`UserContent`（string | 数组）：

```cpp
inline void to_json(nlohmann::json& j, const UserContent& c) {
    std::visit([&](const auto& v){ j = v; }, c);
}
inline void from_json(const nlohmann::json& j, UserContent& c) {
    c = j.is_string() ? UserContent(j.get<std::string>())
                      : UserContent(j.get<std::vector<ContentBlock>>());
}
```

## 6. 设计决策与权衡

### 决策 1：`std::variant` 而非类继承体系

- 问题：如何表达 pi 的 tagged union 消息模型？
- 候选：A. `variant` + visit；B. 抽象基类 `AgentMessageBase` + 各角色派生 + `unique_ptr` + `dynamic_cast`/visitor 双分派。
- 选择：A。理由：值语义（拷贝/比较/放 vector 免堆分配）、visit 穷尽性检查（编译期保证处理所有角色，新增角色时所有遗漏的 visit 立即编译失败——这是把「忘记处理新消息类型」从运行期 bug 变成编译期错误）；pi/tau 的判别联合心智模型直接映射。B 的问题：到处 `unique_ptr` 拷贝语义、`dynamic_cast` 散落、类型闭合性无保证。
- pi 的做法：TS 判别联合（`discriminator="role"`）；tau：Pydantic tagged union。语义同构。

### 决策 2：wire 类型成员名直接用 camelCase

- 问题：C++ 惯例 snake_case 与 wire 的 camelCase 不一致，转换层写在哪？
- 候选：A. snake_case 成员 + 手写逐字段 to_json/from_json 映射；B. camelCase 成员 + 宏自动生成。
- 选择：B。理由：wire 类型是「数据搬运工」，字段与 JSON 一一对应减少一层心智翻译和一堆映射代码；宏 `NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE_WITH_DEFAULT` 直接可用。限定范围：**仅 wire 结构体**（message/events 及后续 provider DTO）；纯内部类型（CancellationToken 等）仍用 snake_case 惯例。
- pi/tau 对照：tau 同思路——Pydantic 字段名即别名。偏差：无。

### 决策 3：L1 事件携带全量 partial（拷贝）

- 问题：pi 的 delta 事件带全量 partial AssistantMessage，C++ 拷贝 vector<ContentBlock> 有成本。
- 候选：A. 事件携带 `shared_ptr<const AssistantMessage>`；B. 直接值拷贝。
- 选择：B（v0.0.1）。理由：先保正确与简单；典型 assistant 消息几十个块、字符串总量 KB 级，delta 频率受网络节流（几十 ms 一个），拷贝成本可忽略。profile 证明是热点再换 A（接口不变，事件结构体内部换持有方式即可）。
- pi 的做法：TS 引用共享同一对象（无拷贝）；我们用值语义换取线程安全（跨线程传递无需同步），是 C++ 下的合理偏差。

### 决策 4：未知字段忽略、未知 role/type 抛错

- 问题：前向兼容策略？pi/tau 新版本加了新消息类型怎么办？
- 选择：`NLOHMANN_DEFINE_TYPE_NON_INTRUSIVE_WITH_DEFAULT` 容忍**未知字段**（忽略）与**缺省字段**（默认值）；但**未知 role/type 判别值抛错**——静默丢弃消息在会话场景是数据丢失，宁可显式失败。未来 v1.0.0 可增加 `custom` 兜底（pi 的 extra 字段策略）。
- tau 对照：`extra="forbid"`（严格禁止未知字段）——我们放宽为忽略，理由：会话文件跨版本互读的实用性优先。

### 决策 5：CancellationToken 放 util 且全测

- 问题：为什么不是用到时再写？
- 选择：v0.0.1 作为一等公民交付。理由：见 §1.3——它是后续每个版本的取消链地基；回调在锁内执行的顺序语义（注册序）、`request` 的幂等、`wait_for` 对虚假唤醒的容忍、析构时回调表已清空（无悬空）——这四点必须有测试钉死。`CombinedCancellation` 同步交付（v0.0.4 的 bash 工具马上要用「超时令牌 + 用户取消令牌」组合）。

### 决策 6：CI 三平台从第一天

- 问题：可以等有网络代码再上 Windows CI 吗？
- 选择：不可以。理由：跨平台从第一天是既定决策（dev-plan §1）；本版本是 CI 成本最低的时刻（无网络依赖、编译快），Windows/MSVC 的差异（路径、`/W4` 警告集、`std::thread` 链接）现在暴露成本最小。依赖选型已规避 Windows OpenSSL 问题（本版本无 cpr）。

**结果**：T1-T12 全部完成。6/6 测试目标、63 个用例全绿（smoke 1 + string 4 + cancel_token 11 + thread_guard 7 + message_json 26 + events_json 14）；release/debug 双预设从零构建通过；`picpp --version` → `picpp v0.0.1`；第一方代码 -Wall -Wextra -Werror 零警告。

**与设计的偏差**（按影响排序）：

1. **nlohmann/json 3.11.3 实测不支持 `std::optional`**（设计 §3.2③ 的说法有误，已用最小程序实证）——8 个含 optional 字段的结构（Usage/DiagnosticError/Diagnostic/TextContent/ThinkingContent/ToolCall/AssistantMessage/BashExecutionMessage）改为手写 to_json/from_json。由此确立的序列化约定反而**更贴近 wire 语义**：`nullopt → 字段整体省略`（而非写 null），恰好对齐 pi/tau「undefined 不落盘」的约定。
2. NLOHMANN 宏必须在 `namespace pi` 内调用——全局作用域的 `pi::` 限定名形式不被查找找到。
3. pi_types 对 nlohmann_json 的链接由 INTERFACE 改为 PUBLIC（开始编译包含其头文件的 message.cpp/events.cpp）。
4. CMake 3.26 拒绝生成无源 STATIC 库 → T1 阶段先 INTERFACE，T4 填入 string.cpp 后转 STATIC。
5. 本机 CMake 3.26.3 拒绝 buildPresets 中的 `args` 键（疑似该版 bug）→ 多配置生成器（Windows VS）改由 configure 预设的 `CMAKE_CONFIGURATION_TYPES` 锁定唯一配置 + testPreset 的 `configuration` 字段，效果等价。
6. 依赖细节：FetchContent 形态下目标名为 `nlohmann_json`（无命名空间）；fmt 无独立 EXAMPLES 选项（并入 FMT_TEST=OFF）；deps.cmake 增加 `CMAKE_POLICY_VERSION_MINIMUM=3.5` 兼容 CMake 4 与 doctest 的旧版声明。
7. 其余小项：`CMAKE_CXX_EXTENSIONS OFF`（严格 -std=c++17）；util/overload.hpp 纳入 namespace pi；test_main 使用 `DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN`；CombinedCancellation 按设计 §5.2 完整交付（含测试）。
8. 过程事件：实现期间有两次外部快照提交（8599589 进度快照、65270b5 中间态），后者曾处于不可构建状态，由 48183ed 修复，HEAD 绿。

**踩坑记录**（写给后续版本与读者）：

- C++ 下 TDD 的红态常表现为**编译/链接失败**（缺头文件）而非断言失败——红提交的语义要按此理解。
- doctest 的 `REQUIRE_MESSAGE` 不接受字符串拼接表达式，改用 `INFO(...) + REQUIRE(...)`。
- `-Wmissing-field-initializers` 会让聚合初始化缺字段触发 -Werror——改用默认成员初始化 + 构造后赋值。
- **variant 的判别字段（role/type）由分发层写入**：测试必须经 variant 序列化再断言，不能从具体结构体直接构造 json（会缺判别字段）。
- LSP 对生成头（version.h）与未拉取的依赖持续误报，以真实 CMake 构建为准。
- **跨平台 CI 首跑暴露的两处平台差异**（本地 macOS 全绿不代表远端绿）：① `cmake --build` 在 VS 多配置生成器上**默认请求 Debug 配置**——当 configure 预设把 `CMAKE_CONFIGURATION_TYPES` 锁为仅 Release 时会报 MSB8013（组合不存在），buildPreset 必须显式加 `configuration` 字段（等价于 `--config`，单配置生成器忽略之）；注意 buildPresets **没有** `args` 字段，`configuration` 才是规范做法。② libstdc++13 下 doctest 的二元断言（CHECK_EQ/NE）不能直接比较 `std::thread::id`——doctest 要字符串化操作数，`operator<<` 的实例化在 `<thread>` 内部找不到可用重载（doctest.h 只前向声明了有限的 `std::operator<<`）；包装为 bool 再断言即可。
