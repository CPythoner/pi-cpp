## 0. 本篇位置

pi-cpp 使用 **C++17** 重写 pi coding agent 的核心能力。行为与 wire 语义以 pi `v0.80.0` 为规范来源；Tau `v0.4.1` 只辅助理解模块划分、算法和工程实现，不作为行为规范来源。

`v0.0.1` 的任务不是做出一个能调用 LLM 的 Agent，而是把后面所有功能依赖的地基一次搭正确：

1. Linux / macOS / Windows 三平台构建与 CI 骨架。
2. `ai`、`agent`、`coding-agent` 三层 SDK 的源码与 public header 边界。
3. pi 兼容方向的消息 / 内容块 / 事件 wire 类型。
4. C++17 下需要的取消、线程和基础工具设施。
5. 手工 JSONL fixture 与确定性单元测试。

## 1. 为什么 v0.0.1 就要确定 SDK 边界

pi 的核心并不是一个 CLI，而是三个可以逐层复用的能力包：

```text
ai
 ↓
agent
 ↓
coding-agent
```

在 C++ 中，这种边界比 TypeScript 更需要尽早明确，因为它会直接决定：

- public header 放在哪里；
- CMake target 的依赖方向；
- 第三方类型是否泄漏到 API；
- 外部工程能否单独链接某一层；
- 后续 install/export/package config 是否容易实现；
- CLI/TUI 是否会反向污染核心业务层。

如果先用一个 `pi_types` 把所有代码堆在 `src/`，再等 Provider、Agent loop、tools 都写完以后拆层，会同时改动 include、target dependency、namespace、测试和调用方。`v0.0.1` 代码量最小，因此这里就是建立长期边界的最低成本窗口。

最终依赖方向固定为：

```text
external C++ app / picpp CLI / TUI
                 │
                 ▼
            coding-agent
                 │
                 ▼
               agent
                 │
                 ▼
                ai
```

依赖只能向下，不能反向。

## 2. v0.0.1 目标与非目标

### 2.1 目标

1. 三平台 configure → build → ctest 基础链路。
2. `picpp --version` 输出 `picpp v0.0.1`。
3. 建立三个 CMake SDK target：`pi::ai`、`pi::agent`、`pi::coding-agent`。
4. public API 进入 `include/pi/...`，不把 `src/` 暴露成 SDK PUBLIC include path。
5. `ai` 层提供 LLM message/content 基础类型、StopReason / Usage / Cost、L1 Provider event、CancellationToken 基础抽象。
6. `agent` 层提供 AgentMessage 和 L2 AgentEvent。
7. `coding-agent` 建立 target、namespace 和 public header 目录骨架，为 `v0.0.4` 的 tools/CodingAgent 预留稳定位置。
8. 4 种 ContentBlock + 7 种 AgentMessage 角色的 JSON round-trip。
9. L1 12 种事件 + L2 10 种事件 round-trip。
10. 三个手工 JSONL fixture 作为内部序列化回归样本。
11. `ai` / `agent` / `coding-agent` 三个独立 public SDK consumer 编译测试。

### 2.2 非目标

本版本明确不做：

- 真实 HTTP / LLM Provider（`v0.0.2`）。
- EventStream 运行时队列（`v0.0.2`）。
- pi reference harness / differential compatibility gate（`v0.0.2`）。
- Agent runLoop（`v0.0.3`）。
- read / write / edit / bash（`v0.0.4`）。
- SessionHeader / SessionEntry 完整持久化模型（`v0.1.0`）。
- `cmake --install` / `find_package(picpp)` 完整安装消费能力（`v0.1.0`）。

### 3.1 public 与 private 的判断标准

只有 `include/pi/...` 属于 SDK public API。

```text
include/pi/...   -> external consumer 可以 include
src/...          -> implementation / private support
apps/picpp/...   -> 官方前端
```

硬约束：

- SDK target 的 PUBLIC include path 只能指向 `include/`。
- `${PROJECT_SOURCE_DIR}/src` 不得作为 SDK PUBLIC include path。
- `cpr`、`reproc++`、`FTXUI` 等第三方实现类型不得进入 public API。
- CLI/TUI 不得 include `src/ai`、`src/agent`、`src/coding-agent` 的 private header。

## 4. CMake SDK target

本版本即建立三个长期 target 名称：

```cmake
pi_ai           -> pi::ai
pi_agent        -> pi::agent
pi_coding_agent -> pi::coding-agent
picpp           -> executable
```

依赖关系：

```cmake
pi_agent        PUBLIC pi::ai
pi_coding_agent INTERFACE pi::agent
picpp           PRIVATE pi::coding-agent
```

对应结构：

```text
picpp
  │
  ▼
pi::coding-agent
  │
  ▼
pi::agent
  │
  ▼
pi::ai
```

`coding-agent` 在 `v0.0.1` 仍是 INTERFACE target，因为还没有 coding-domain 实现源码；但 target 名、依赖方向和 public header 位置已经固定。`v0.0.4` 只需要把它从骨架扩展成真正的 library，不再重新设计项目结构。

三个 SDK target 都显式声明自己的 build-time public include contract：

```cmake
target_include_directories(pi_ai PUBLIC
    "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
)

target_include_directories(pi_agent PUBLIC
    "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
)

target_include_directories(pi_coding_agent INTERFACE
    "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
)
```

因此 `coding-agent` 的 public header 可见性不依赖 `agent` 恰好传播同一个 include root。

`v0.1.0` 再补 `INSTALL_INTERFACE`、export targets 与 package config。

## 5. C++ namespace 与模块名

模块名与 pi 保持一致：

```text
ai
agent
coding-agent
```

C++ 标识符不能包含 `-`，因此 canonical namespace 是：

```cpp
pi::ai
pi::agent
pi::coding_agent
```

CMake target 名可以保留连字符：

```cmake
pi::ai
pi::agent
pi::coding-agent
```

`v0.0.1` 不提供顶层 `pi::Type` 兼容 alias。public API、测试和示例统一使用所属 SDK 的 canonical namespace，避免第一版就形成两套对外类型名称。

## 6. 类型责任划分

### 6.1 ai 层

`include/pi/ai/message.hpp` 负责 LLM / Provider 世界的类型：

```text
StopReason
Cost / Usage / Diagnostic
TextContent
ThinkingContent
ImageContent
ToolCall
ContentBlock
UserMessage
AssistantMessage
ToolResultMessage
Message
```

核心关系：

```cpp
using ContentBlock = std::variant<
    TextContent,
    ThinkingContent,
    ImageContent,
    ToolCall>;

using Message = std::variant<
    UserMessage,
    AssistantMessage,
    ToolResultMessage>;
```

这些类型可以脱离 Agent 独立使用，因此属于 `ai`。

### 6.2 agent 层

`include/pi/agent/message.hpp` 在 `ai::Message` 基础上增加应用层消息：

```text
BashExecutionMessage
CustomMessage
BranchSummaryMessage
CompactionSummaryMessage
```

```cpp
using AgentMessage = std::variant<
    ai::UserMessage,
    ai::AssistantMessage,
    ai::ToolResultMessage,
    BashExecutionMessage,
    CustomMessage,
    BranchSummaryMessage,
    CompactionSummaryMessage>;
```

保持 pi 的双层消息模型：

```text
Provider/LLM Message
        ↓
AgentMessage
```

真正发给模型时，后续 Agent 在边界处把 AgentMessage 降维成 LLM Message。

## 7. L1 / L2 事件分层

### 7.1 L1：ai Provider events

`include/pi/ai/events.hpp` 描述 AssistantMessage 如何流式生成：

```text
start
text_start / text_delta / text_end
thinking_start / thinking_delta / thinking_end
toolcall_start / toolcall_delta / toolcall_end
done / error
```

共 12 种。

它可以被不使用 Agent 的独立 Provider consumer 使用，所以归属 `ai`。

### 7.2 L2：agent events

`include/pi/agent/events.hpp` 描述 Agent 生命周期：

```text
agent_start / agent_end
turn_start / turn_end
message_start / message_update / message_end
tool_execution_start / update / end
```

共 10 种。

`message_update` 可嵌入 `ai::AssistantMessageEvent`，依赖方向自然是：

```text
agent -> ai
```

## 8. wire 与 JSON 规则

### 8.1 规范来源

所有 wire 行为按以下优先级裁决：

> **pi `v0.80.0` 可观察行为 > pi-cpp 明确兼容规范 > Tau `v0.4.1` 实现参考**

### 8.2 判别字段

| 类型 | 判别字段 | 典型值 |
|---|---|---|
| Message / AgentMessage | `role` | user / assistant / toolResult / bashExecution / custom / branchSummary / compactionSummary |
| ContentBlock | `type` | text / thinking / image / toolCall |
| L1 event | `type` | start / text_* / thinking_* / toolcall_* / done / error |
| L2 event | `type` | agent_* / turn_* / message_* / tool_execution_* |

### 8.3 `std::variant`

TypeScript tagged union 在 C++17 中映射为 `std::variant`，JSON serializer 负责写入 `role` / `type` 判别字段。

优势：值语义、不需要为每条消息单独堆分配、`std::visit` 易于发现遗漏分支，并与 pi 判别联合的模型直接对应。

### 8.4 optional 字段

以 nlohmann/json 3.11.3 的实际验证为准：

- 简单字段可以用 NLOHMANN 宏；
- 含 `std::optional` 的结构手写 `to_json/from_json`；
- `nullopt` 序列化为字段省略，不写 JSON `null`；
- variant 判别字段由 variant serializer 写入。

## 9. CancellationToken

Abort/cancel 最终贯穿：

```text
CodingAgent
   ↓
Agent
   ↓
Provider / Tool
   ↓
HTTP / process tree
```

所以 `v0.0.1` 即提供：

```cpp
#include <pi/ai/cancellation.hpp>

pi::ai::CancellationToken token;
```

接口：

```cpp
void request();
bool requested() const noexcept;
bool wait_for(std::chrono::milliseconds timeout) const;
std::uint64_t registerCallback(Callback cb);
bool unregisterCallback(std::uint64_t id);
```

这是项目自己的 C++17 cancellation abstraction，不宣称与 `std::stop_token` 完全等价。

`v0.0.2` 在真实 HTTP 前完成并发加固：

- request 锁内只做状态切换与 callback snapshot；
- callback 解锁后执行；
- unregister/request/destructor race 有明确语义和测试。

## 11. 测试结构

### 11.1 行为测试按 SDK 层链接

message/event/cancellation 行为测试直接通过 canonical public headers 和所属层 target 消费：

```text
test_cancel_token -> pi::ai
test_message_json -> pi::agent
test_events_json  -> pi::agent
```

只有 `string` / `ThreadGuard` 这类当前仍属于 private support 的测试允许通过 PRIVATE include 访问 `src/`；这不会扩大 SDK public include contract。

未知 `role` 的测试只约束“抛出 `std::runtime_error` 且诊断中包含实际 role 值”，不把错误前缀的逐字文本冻结成 public compatibility contract。

### 11.2 三层独立 SDK consumer tests

三个 consumer 都只使用 canonical `<pi/...>` public headers，并且分别只链接对应层：

```text
test_ai_sdk.cpp
  -> link pi::ai

test_agent_sdk.cpp
  -> link pi::agent

test_coding_agent_sdk.cpp
  -> link pi::coding-agent
```

其中不添加 `${PROJECT_SOURCE_DIR}/src` include path。

这能直接验证：

- `ai` 可脱离 agent/coding-agent 使用；
- `agent` 只依赖 ai；
- `coding-agent` consumer 不依赖 CLI/TUI；
- public header 的 canonical include 路径真实可用。

## 13. 实现中确认的工程经验

### 13.1 nlohmann/json

nlohmann/json 3.11.3 在本项目实际使用下不能直接依赖“optional 自动序列化”的假设，因此含 optional 的 DTO 明确手写 serializer；字段省略/null 语义也由项目控制。

### 13.2 CMake

- 无源 STATIC library 在部分 CMake 版本上不可行；未有源码的 coding-agent 在本版本使用 INTERFACE target。
- 每个 SDK target 显式拥有自己的 public include contract，不依赖下层 target 的偶然传播。
- FetchContent 下第三方 target 名以实际生成结果为准。
- MSVC 多配置生成器显式处理 configuration。
- 第一方 warning-as-error 与第三方 SYSTEM include 隔离。

### 13.3 三平台第一天开始

Windows VS 多配置、libstdc++ 与 doctest 的差异都说明：跨平台不能等功能完成后再补。
